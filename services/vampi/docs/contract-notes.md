# VAmPI: contract notes

Observed behaviour of the local VAmPI image (`erev0s/vampi`, pinned by digest in
`docker-compose.yml`) that differs from its OpenAPI document (`../openapi.yaml`) or that a case must
know about. The image runs in two modes, `vampi-secure` (`vulnerable=0`) and `vampi-vulnerable`
(`vulnerable=1`); an entry applies to both unless it names one. Each entry says how to reproduce it
and how it is tracked. At design time every entry becomes a designed case, and a defect becomes a
known gap linked to its tracker issue.

**Status:** `untracked` (observed, no issue yet) · `tracked` (issue filed, key given) · `by-design`
(a difference to tolerate, not a defect).

| Id | Observation | Reproduce | Kind | Status |
|---|---|---|---|---|
| VN-01 | A fresh container has no database tables. Every read that touches storage (`GET /books/v1`, `GET /users/v1`, `GET /users/v1/{username}`) answers `500` until `GET /createdb` has run; the spec declares only `200` for the list reads. | `GET /books/v1` on a container just started | environment limit | `by-design` |
| VN-02 | Unhandled errors answer with the Werkzeug interactive debugger page (`text/html`, `EVALEX = true`): stack trace, the failing SQL statement with every column of the table, and source paths. Every answer carries `Server: Werkzeug/<version> Python/<version>`. Same in both modes. | `GET /books/v1` on a fresh container (VN-01) | information exposure | `untracked` |
| VN-03 | `401` comes in two formats. A missing token, or an `Authorization` header that is not `Bearer`, is refused by the framework with `application/problem+json` `{type, title, status, detail}` ("No authorization token provided"). A bearer token that cannot be decoded reaches the handler and answers the declared `{status: "fail", message}` ("Invalid token. Please log in again."). The spec declares only the second, and `GET /me` lists its `401` messages as a value set that lacks the first. | `GET /me` and `GET /books/v1/<UNKNOWN_TITLE>` without `Authorization`, with `Basic <ANY>` and with `Bearer <NOT_A_JWT>` | contract drift | `untracked` |
| VN-04 | An unknown path answers `404` as `application/problem+json`. No operation declares it; it is the framework's format, not the handlers' `{status, message}`. | `GET /<UNKNOWN_PATH>` | contract gap | `by-design` |
| VN-05 | `GET /createdb` is not safe: it creates the tables and seeds users and books. It is left out of the smoke spec and out of read-only intake; a case that needs seeded data treats it as a write. The DAST lane removes it from the definition ZAP imports: until 2026-10-13 the import called it at the start of every scan, because ZAP's URL exclusions do not apply to the import, and the reset deleted the users the scan had registered. | `GET /createdb` (not sent at intake) | contract gap | `by-design` |
| VN-06 | `GET /users/v1/_debug` returns every user's details, password included, to any caller; the spec's schema has the field, so it conforms to the document while exposing credentials. It is left out of the smoke spec so no run stores passwords in its evidence, and out of the DAST scan (`dast-exclude.txt`) so ZAP never holds them. Not called at intake. | `GET /users/v1/_debug` (not sent at intake) | information exposure | `untracked` |
| VN-07 | A duplicate registration and a failed login answer `200` with `{status: "fail", message}`, where the spec declares `400`. The pack fixtures register the users of the `login` credentials on every worker and rely on this: a user that already exists is not an error, and its next login proves the password. | `POST /users/v1/register` twice with one username | contract drift (status) | `untracked` |
| VN-08 | `GET /books/v1/{book_title}` answers `200` with one object `{book_title, owner, secret}`; the spec declares an array of them. Same in both modes. | as the owner, `GET /books/v1/<BOOK_TITLE>` (TC-BOOK-01) | contract drift (shape) | `untracked` |
| VN-09 | Another user's book: `vampi-secure` answers `404` with the `fail` envelope ("Book not found!"), the same as a title no book has, so not even the book's existence leaks. `vampi-vulnerable` answers `200` with the owner and the secret: Broken Object Level Authorization (OWASP API1:2023), the flaw that mode exists to show. | as another user, `GET /books/v1/<BOOK_TITLE>` (TC-BOOK-02) | authorization (vulnerable mode) | `by-design` |
| VN-10 | A registration answered `500` once, while several workers registered the same users at the same moment (2026-10-12, secure mode); sequential runs never did. The likely cause is the unique username racing between the existence check and the insert. The pack fixtures accept a failed registration only when the same credentials then log in. | several workers sending `POST /users/v1/register` for one username at once | robustness (concurrency) | `untracked` |
| VN-11 | `vampi-vulnerable` builds the SQL of `GET /users/v1/{username}` from the path segment: a single quote answers `500` with the SQLite syntax error in the debugger page (VN-02). The DAST lane reports it as SQL Injection (ZAP rule 40018, high risk, low confidence) and its 5xx answers as rules 100000 and 100001. `vampi-secure` answers the same input `404` "User not found". ZAP finds it only with URL-path injection on (`scanner.injectable=19`): by default it injects the query and the body, not path segments. | `GET /users/v1/<USERNAME>'` without a token; `QA_ENV=local-vulnerable npm run lanes:dast -- --service vampi --out vampi-vulnerable --actor anonymous` (a token reaches VN-15) | injection (vulnerable mode) | `by-design` |
| VN-12 | No answer carries `X-Content-Type-Options: nosniff` or `Cross-Origin-Resource-Policy` (ZAP rules 10021 and 90004, low; the DAST lane reports only 10021 since it stopped loading ZAP's beta rules, GATE-26), and the `Server` header names Werkzeug and Python versions (10036, low; VN-02). A username holding markup is stored and listed unescaped by `GET /users/v1` (40014, low, low confidence): harmless as `application/json` while browsers do not sniff it, which is what the missing `nosniff` leaves open. Same in both modes. | any request, read the headers; the DAST lane in either mode | hardening (headers) | `untracked` |
| VN-13 | The served `openapi.json` declares `servers: [{url: ""}]` (the tracked `../openapi.yaml` declares `http://localhost:5000`). A relative server resolves against the document's own URL, so a tool that reads the document from its URL sends every operation to `/openapi.json/<path>` and gets `404`: a ZAP scan built that way reached no operation. The DAST lane saves the document and passes the base URL with `-O`. | `GET /openapi.json`, read `servers` | contract gap | `untracked` |
| VN-14 | `GET /createdb` seeds books with random titles, and two of them can collide on the unique `book_title`: the call then answers `500` (`UNIQUE constraint failed: books.book_title`) and the database is left half seeded. Seen once in CI right after the container turned healthy. Calling it again reseeds with new titles, so `create-db.mjs` retries a 5xx a few times. | `GET /createdb` repeated until it answers `500` | robustness (seed data) | `untracked` |
| VN-15 | `vampi-vulnerable` validates the e-mail of `PUT /users/v1/{username}/email` with a regular expression that backtracks catastrophically (its own comment calls it Regex DoS): a crafted value keeps the single worker at 100% CPU and the API stops answering every caller until the container restarts. The check runs only after the token is validated, so an unauthenticated scan never reaches it. An authenticated ZAP scan did on 2026-10-13: the API stopped answering after about five minutes and the scan waited at 77%. `vampi-secure` validates the e-mail with another expression. The `dast` workflow therefore scans the vulnerable mode without a token, and the DAST lane stops a scan whose API stops answering. | an authenticated `QA_ENV=local-vulnerable npm run lanes:dast -- --service vampi` (implementation: `api_views/users.py`) | denial of service (vulnerable mode) | `by-design` |
| VN-16 | An authenticated ZAP scan of `vampi-secure` on 2026-10-13 reported SQL Injection (rule 40018, high, medium confidence) on `POST /users/v1/register`, parameter `username`, from boolean probes (`name1 AND 1=1 -- ` against `name1 AND 1=2 -- `). It is false: the handler looks the name up with `User.query.filter_by(username=...)`, a bound ORM query, before it inserts. The two probes answered differently because registering is stateful: one name had been registered earlier in the scan ("already exists") and the other had not. An unauthenticated scan of the same code did not report it. [`dast-false-positives.tsv`](../dast-false-positives.tsv) marks it, so the quality gate does not count it. | an authenticated `npm run lanes:dast -- --service vampi`; implementation: `register_user` in `api_views/users.py` | false positive (scanner) | `by-design` |

The tracked `../openapi.yaml` is the upstream document with one edit: the example `auth_token` of
`POST /users/v1/login` (a real-looking JWT) reads `<AUTH_TOKEN>`, so no token-shaped value is
committed. Examples are not part of the digest.

VN-01 to VN-04 were measured read-only on both containers on 2026-10-12. VN-05 and VN-06 come from
the spec and the implementation, without a call. VN-08 and VN-09 were measured by the spec run of
the book registry in both modes on 2026-10-12; VN-07 comes from the implementation, and the pack
fixtures depend on it. VN-11 to VN-13 come from ZAP 2.17.0 API scans of both containers on
2026-10-12, run without a token: of the 14 operations, the 6 that need a bearer token
(`GET /me`, `POST /books/v1`, `GET /books/v1/{book_title}`, `DELETE /users/v1/{username}` and
the two `PUT /users/v1/{username}/...`) answered `401` before their handlers ran, so the scan
judged only the other 8. A scan is an active attack that writes (it registers users and changes their passwords and
e-mails), so it runs only against these disposable containers. VN-10 was seen in a parallel spec
run in secure mode on 2026-10-12, and VN-14 once in CI while the database was being created. VN-15
and VN-16 come from authenticated ZAP scans on 2026-10-13 (FUT-10), which reached the operations an
unauthenticated scan could not. The
feature contracts in [`features/`](features/) hold the full measurements and the implementation
reading: [books](features/books.md).

The error formats themselves are catalogued in `../error-envelopes.json`; VN-01 to VN-04 are why
`server-error` and `problem` exist there next to the declared `fail`.
