# Petstore contract notes

Observed behaviour of the local Petstore image (`swaggerapi/petstore3:1.0.28`) that differs from its
OpenAPI document (`../openapi.json`) or that a case must know about. Each entry says how to reproduce
it and how it is tracked. At design time every entry becomes a designed case, and a defect becomes
a known gap linked to its tracker issue.

**Status:** `untracked` (observed, no issue yet) · `tracked` (issue filed, key given) · `by-design`
(a difference to tolerate, not a defect).

| Id | Observation | Reproduce | Kind | Status |
|---|---|---|---|---|
| PN-01 | A pet body without `id` answers `500` with a log reference and stores nothing: the service never assigns an id. Earlier this was put down to a wrong-typed or missing `name`, but with an `id` present a numeric `name` is stored as text and a missing `name` is stored too, both with `200` (2026-10-10). | `POST /pet` with `{"name": "x", "photoUrls": []}` | defect | `untracked` |
| PN-02 | "Not found" answers (pet, order, user) are plain text (`Pet not found`). The content type follows `Accept`: `application/xml` with no `Accept` or a wildcard, `application/json` when JSON is asked, although the body is not JSON. The document declares no body for these 404s. | `GET /pet/{id}` for an id that was never created, with and without `Accept: application/json` | contract drift | `untracked` |
| PN-03 | Input errors name the offending parameter only inside `message`; no key carries the field. Cases check the error kind; which field was blamed is not observable. | `GET /pet/findByStatus?status=lost` | contract gap | `by-design` |
| PN-04 | `shipDate` is echoed with a `+00:00` offset where the request sent `Z` (`2026-10-09T10:00:00.000Z` comes back as `2026-10-09T10:00:00.000+00:00`). Same instant, different text. | `POST /store/order`, then `GET /store/order/{id}` | format difference | `by-design` |
| PN-05 | The `api_key` header is accepted with any value and not required for the operations used so far, so this API cannot demonstrate an authorization matrix (see backlog FUT-07). `petstore_auth` is not checked either: `GET /pet/findByStatus`, `GET /pet/{petId}` and `GET /store/inventory` answer `200` with no credentials at all (2026-10-13), which lets the performance lane measure them anonymously (`../perf.json`). | Any request with or without `api_key`; those three `GET`s with no `api_key` and no token | environment limit | `by-design` |
| PN-06 | `PUT /pet` stores a pet whose `status` is outside the enum (`lost`) or that lacks the required `name`, and answers `200`. Found while designing the shared-data guard: a probe of this kind corrupted seed pet 1 until it was restored by hand. Cases that probe it must use a dedicated pet or run inside `withResourceGuard(..., { expectChange: false })`. | `PUT /pet` with `{"id": <id>, "name": "x", "photoUrls": [], "status": "lost"}` | defect | `untracked` |
| PN-07 | Answers disclose the implementation: input errors name the Java type (`class java.lang.Long`) and echo the raw input, injection strings included; every answer carries a `Server` header with the web server version; `OPTIONS` returns a WADL document naming the framework version; a body that cannot be read answers with the model class name (`io.swagger.petstore.model.Order`) or a dump of the internal OpenAPI model. | `GET /pet/abc`; `OPTIONS /store/order/1`; `POST /pet` with an empty JSON body | information exposure | `untracked` |
| PN-08 | Error formats the document does not declare: unsupported methods answer `405` with a `{code, message}` JSON body; with `Accept: application/xml`, `400` and `405` answers use an `<ApiError>` XML body; an empty `tags` answers `400` with the plain text `No tags provided. Try again?`; a path of about 8 KB answers `414` as an HTML page without CORS headers; an unsupported request content type answers `415`. The declared `422` was produced by no write tried on 2026-10-10. | `GET /pet`, `GET /store/order`, `GET /user/`; `GET /pet/abc` with `Accept: application/xml`; `GET /pet/findByTags?tags=` | contract gap | `untracked` |
| PN-09 | The inventory is described as pet counts by status, but its keys are order statuses (`placed`, `approved`, `delivered`) and each value is the sum of the quantities of the orders in that status. | `GET /store/inventory`, compared with `GET /store/order/1` to `/3` | contract drift | `untracked` |
| PN-10 | `findByStatus` is described as taking comma-separated values. A comma list answers `400`, and with repeated `status` parameters only the first is used and validated (`?status=available&status=lost` answers `200`). | `GET /pet/findByStatus?status=available,sold`; `?status=available&status=lost` | contract drift | `untracked` |
| PN-11 | `findByTags` is described as taking comma-separated tags. A comma list is matched as one literal tag and returns `[]`; repeated `tags` parameters list a pet once per matching tag, so the same tag twice returns every match twice. | `GET /pet/findByTags?tags=tag1,tag2`; `?tags=tag1&tags=tag1` | defect | `untracked` |
| PN-12 | `GET /user/login` answers `200` with a new session for any input: no parameters, an unknown user or a wrong password. The declared `400` is never produced. Its `X-Expires-After` header is Java date text rather than `date-time`, and with `Accept: application/json` the plain-text body is labelled JSON. | `GET /user/login` without parameters; the same with `Accept: application/json` | defect | `tracked` (`LOCAL-4`) |
| PN-13 | Reading a user returns its stored `password` to any caller, anonymous included, and the answers to `POST /user` and `PUT /user/{username}` echo it too. The schema has the field, so this conforms to the document, but it exposes a credential. | `GET /user/<SEED_USERNAME>`; the answer of `POST /user` for a user the case creates | information exposure | `tracked` (`LOCAL-3`) |
| PN-14 | XML representations differ from the schema: the user root element is `User` (declared `user`); an order's `shipDate` is epoch milliseconds; the inventory, declared JSON only, is served as XML when asked. An unsupported `Accept` answers `200` JSON instead of `406`. | `GET /user/<SEED_USERNAME>`, `GET /store/order/1`, `GET /store/inventory` with `Accept: application/xml`; `GET /pet/1` with `Accept: text/plain` | format difference | `by-design` |
| PN-15 | What an invalid id is stays undefined. Zero and negative pet or order ids answer `404`, not the declared `400`. The order read's prose says ids up to 5 or above 10 are valid and others raise errors; every unknown id answers `404`. | `GET /pet/0`, `GET /pet/-1`, `GET /store/order/7` | contract drift | `untracked` |
| PN-16 | Path ids are parsed leniently: a leading `+`, a leading zero and a trailing slash resolve to the same record. | `GET /pet/+1`, `GET /pet/01`, `GET /store/order/01` | format difference | `by-design` |
| PN-17 | An order without `status` makes `GET /store/inventory` answer `500` to every caller until that order is deleted. A body of `{}` creates such an order with id `0`. | `POST /store/order` with `{"id": <ORDER_ID>}`, then `GET /store/inventory`; clean up with `DELETE /store/order/<ORDER_ID>` | defect | `tracked` (`LOCAL-2`) |
| PN-18 | A pet created from a form-encoded body with `tags` stores each tag as a bare string, drops a nested `category` and keeps only the last `photoUrls`. While it exists, `GET /pet/findByTags` answers `500` to every caller. | `POST /pet` as `application/x-www-form-urlencoded` with `id=<PET_ID>&name=x&photoUrls=a&tags=<TAG>`, then `GET /pet/findByTags?tags=tag1`; clean up with `DELETE /pet/<PET_ID>` | defect | `untracked` |
| PN-19 | `POST /user` with `{}` answers `200` and stores a record without a username (id `0`). From then on every read of an unknown username answers `500` instead of `404`. No operation can address that record: only restarting the service clears it. A body with other fields but no `username` answers `500`. | `POST /user` with `{}`, then `GET /user/<UNKNOWN_USERNAME>` | defect | `tracked` (`LOCAL-1`) |
| PN-20 | Creating with an id or username that already exists replaces the stored record and answers `200`, for pets, orders and users alike. | `POST /pet`, `POST /store/order` or `POST /user` twice with the same id or username | defect | `untracked` |
| PN-21 | Writes store input the document refuses: a `status` outside its value set (`POST /pet`, `POST /pet/{petId}`, `POST /store/order`; each new order status becomes an inventory key), a pet without `photoUrls` or with a `null` name, an order `quantity` of `0` or below (a negative one lowers the inventory), an order for a pet that does not exist. Wrong JSON types are coerced rather than refused in some fields (a number stored as text, `"true"` as a boolean, fractions truncated), and an impossible date-time rolls over into a valid one. `PUT /pet` is PN-06. | `POST /store/order` with `"status": "<OUT_OF_SET>"`, then `GET /store/inventory` | defect | `untracked` |
| PN-22 | `DELETE` answers `200` for a pet, order or user that does not exist, including a second delete of the same record. The declared `404` never appears. | `DELETE /pet/<UNUSED_ID>`, `DELETE /store/order/<UNUSED_ID>`, `DELETE /user/<UNKNOWN_USERNAME>` | contract drift | `untracked` |
| PN-23 | `POST /pet/{petId}` with only `name` stores the pet without its `status`; without `name` it answers `400` `No Name provided. Try again?` although the document makes `name` optional. It reads query parameters only and ignores a form body. An unknown pet answers an undeclared `404`. | `POST /pet/<PET_ID>?name=x`, then `GET /pet/<PET_ID>` | defect | `untracked` |
| PN-24 | `POST /pet/{petId}/uploadImage` answers with a `Pet` instead of the declared `ApiResponse`, and appends a server temporary-file path (`/tmp/inflector<digits>.tmp`) to the pet's `photoUrls`. | `POST /pet/<PET_ID>/uploadImage` with a small binary body | information exposure | `untracked` |
| PN-25 | User writes depart from the usual create and update shape: an omitted `id` is stored as `0`, so ids are not unique; `PUT /user/{username}` replaces the whole record, clearing fields it was not sent, and a body `username` or `id` that differs from the path renames or re-keys the user; `createWithList` answers with the whole array, not one `User`. | `PUT /user/<USERNAME>` with `{"username": "<OTHER_USERNAME>"}`, then `GET /user/<USERNAME>` | contract gap | `untracked` |
| PN-26 | Pet requests are not thread-safe: every pet lives in one unsynchronised list, so while one caller creates, updates or deletes pets, a search running at the same moment can answer `500` and a pet just created with `200` can be lost (`404` on the next read, missing from `findByTags`). The suite runs the pack one worker at a time (`workers` in `../service.json`) until `LOCAL-5` ships; users and orders share the pattern (`LOCAL-6`, `LOCAL-7`, not reproduced). | two callers at once: `POST /pet` and `DELETE /pet/<PET_ID>` on their own ids, and `GET /pet/findByStatus?status=sold` | defect | `tracked` (`LOCAL-5`) |
| PN-27 | A ZAP scan of the local image on 2026-10-13 reported SQL Injection (rule 40018, high, low confidence) on `PUT /pet`, `POST /pet/{petId}`, `PUT /user/{username}` and `DELETE /user/{username}`, from boolean and error probes such as `ZAP AND 1=1 -- ` against `ZAP AND 1=2 -- `. It is false: the image has no SQL layer. None of the 89 libraries in its `WEB-INF/lib` is a database driver, ORM or query builder, and pets, users and orders live in Java lists inside `PetData`, `UserData` and `OrderData`. The probes answered differently because a write echoes the value it stored (`PUT /pet` returns the pet with the injected `name`) and because the scan's own writes changed the records between probes (PN-20, PN-26); a second scan the same day, with one thread, did not report it. [`dast-false-positives.tsv`](../dast-false-positives.tsv) marks it for the scans where the probes meet changed records again. | `npm run lanes:dast -- --service petstore`; the libraries: `docker compose exec petstore sh -c 'ls /tmp/jetty-*/webapp/WEB-INF/lib'` | false positive (scanner) | `by-design` |
| PN-28 | Every answer, the `OPTIONS` preflight included, carries `Access-Control-Allow-Origin: *` with `GET, POST, DELETE, PUT` and the `api_key` and `Authorization` headers allowed. ZAP reports it as Cross-Domain Misconfiguration (rule 10098, medium). It is a public example API's choice: no answer sets `Access-Control-Allow-Credentials`, so a browser never attaches cookies to a cross-origin call, and the `api_key` is not checked (PN-05). An API that authenticates with cookies would need this fixed. | `GET /pet/findByStatus?status=available` with `Origin: https://<OTHER_ORIGIN>` | information exposure | `by-design` |
| PN-29 | Compared with release 1.0.26, the differential lane's reference, 1.0.27 made `status` of `GET /pet/findByStatus` and `tags` of `GET /pet/findByTags` required in the contract, and a request without them now answers `400` with the `{code, message}` JSON envelope (`Input error: missing required query parameter`), where 1.0.26 answered `400` with plain text (`No status provided. Try again?`) under `Content-Type: application/json`. Every other request the lane sends answers the same, apart from the seed orders' `shipDate`, which each container sets when it starts; 1.0.27 and 1.0.28 answer every request the same. [`diff.json`](../diff.json) accepts these differences and makes `shipDate` volatile for that comparison. | `npm run petstore:reference:up`, then `npm run lanes:diff -- --service petstore --reference reference`; by hand: `GET /pet/findByStatus` without `status` on each release | version change | `by-design` |

PN-07 to PN-16 were measured read-only at intake on 2026-10-10. PN-17 to PN-25 and the revised
PN-01 come from an execution-mode run the same day that wrote only to records it created and deleted
them afterwards; PN-19 needed a restart of the service. The feature contracts in
[`features/`](features/) hold the full measurements. PN-27 and PN-28 come from the DAST lane on
2026-10-13: its scan writes to the local image only, and the pack's recovery restarts the image
afterwards. PN-29 comes from the differential lane on 2026-10-14, read-only, which compared
releases 1.0.26 and 1.0.28; 1.0.27 was compared by hand and answered the same as 1.0.28, which is
why the reference is 1.0.26.

**Destructive reproductions.** PN-17, PN-18 and PN-19 leave a record that breaks a read for every
caller. A case that reproduces one of them is `@destructive` (`.claude/rules/tagging.md`): it never
runs next to other cases against shared data, and PN-19 needs the service restarted afterwards.

The error formats themselves are catalogued in `../error-envelopes.json`; PN-01 and PN-02 are why
`server-error` and `not-found` exist there.
