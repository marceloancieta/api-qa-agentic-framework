# `Pets` test cases: updates and images

Contract: [`docs/features/pet.md`](../docs/features/pet.md). This file continues the `PET`
numbering of [`pet.md`](pet.md), which also holds the design notes that apply to every `PET` file:
the security term and parity cases, defects designed as defects, tolerated notes, plain-text
refusals and the absence of a latency budget.

## Integrity questions

Asked for every write in this file (L-20, L-25, L-35, L-37, L-59):

- **Who else writes these fields?** `name` and `status`: `POST /pet` (TC-PET-03 to TC-PET-06 in
  `registry/pet.md`), `PUT /pet` and the form update here. `photoUrls`: `POST /pet`, `PUT /pet`
  and `uploadImage`. A mishandled field is checked on each of them (TC-PET-30 to TC-PET-35 are the
  `PUT` siblings of the create cases; TC-PET-44 is the form sibling of TC-PET-05).
- **Preserve-on-omit.** Every case that expects a field kept first sets it to a value other than
  the builder default: a generated `<NAME>`, a status other than `available`, two photo URLs, a
  category and a `<TAG>` (L-20). The partial-write cases are TC-PET-42, TC-PET-43 and TC-PET-47.
- **Own records.** Each case creates its pet `<PET_ID>`; no seed pet is written. Uploads append to
  `photoUrls` (PN-24), another reason never to upload to a seed pet.
- **State after an error.** Every refused write reads its pet back and compares it with the state
  before the write (`expectSameState`); writes to `<UNKNOWN_PET_ID>` read it back as `404`.
- **Cleanup.** Every case deletes its pet and confirms the delete with a `404` read (PN-22).
- **Records that break reads for others.** None known from these operations; the form-encoded
  `PUT /pet` with `tags` is assumed to share PN-18 with the create and is not designed (only the
  create reproduces it, TC-PET-16).
- **Not designed.** A form body on `POST /pet/{petId}` (W-10): the contract declares query
  parameters only. The `uploadImage` body probes `p-bca1727c7d` and `p-bb99adee9c` (wrong type,
  `null`) have no meaning for an `application/octet-stream` body; TC-PET-48 covers the empty body
  and TC-PET-51 the content type. Where `additionalMetadata` goes is open question A10 of the
  contract, so no case asserts on it.

## Case details

### TC-PET-28

- **Preconditions**: `default`; a pet `<PET_ID>` created by the case with every field.
- **Request**: `PUT /pet` with `<PET_ID>` and a new `<NAME>`, `<OTHER_STATUS>`, category, tags and
  photo URLs, then `GET /pet/<PET_ID>`.
- **Expected**: `200` `Pet` equal to the sent body; the read-back equals it field by field.
- **Verification**: state comparison with `expectSameState` against the sent body.
- **Cleanup**: delete, confirmed by a `404` read.
- **Tags**: `@smoke @data-integrity`

- **Cleanup**: if the read shows a pet, delete it and confirm with a `404` read.
