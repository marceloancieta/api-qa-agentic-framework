# `Pets` test cases: create, read and delete

Contract: [`docs/features/pet.md`](../docs/features/pet.md). Departures:
[contract notes](../docs/contract-notes.md).

The `PET` cases are split by sub-area, numbered across the files (the registry rule, "Files are
containers"):

| File | Holds | Cases |
|---|---|---|
| `registry/pet.md` | create, read by id, delete | TC-PET-01 to TC-PET-27 |
| `registry/pet-update.md` | `PUT /pet`, the form update, image upload | TC-PET-28 to TC-PET-53 |
| `registry/pet-search.md` | `findByStatus`, `findByTags` | TC-PET-54 to TC-PET-66 |

Requirement ids are the contract's business rules: `REQ-PET-NN` is rule NN of the
[contract](../docs/features/pet.md#business-rules). Each file declares the ones it cites.

## Design notes

- **Floor and gap** are computed by `npm run coverage:status` from the endpoints above, never written
  here (L-08). Cases in `beyond_floor` come from measurement or risk, not from the contract (L-55).
- **Security term.** The floor gives every operation two security cases (no credential, invalid
  credential). The service enforces no credential and that is tolerated (PN-05, `by-design`), and a
  real authorization matrix is out of scope (backlog FUT-07). These are therefore parity cases:
  `anonymous` and an unissued `api_key` must be answered like `default`; a difference is a finding.
  They never assert a `401`. Here they are TC-PET-26 and TC-PET-27.
- **Defects are designed as defects.** A case asserts the contract's behaviour, or the security
  expectation where the contract is silent. Its details record the observed departure and its
  contract note. No `PET` note is tracked yet, so the Defect column is empty, and each departure
  reads "Departure: PN-NN (untracked)". Automate decides whether to file it or tolerate it.
- **Tolerated notes** (`by-design`): PN-03 (the field is named only inside the message, so cases
  assert the error kind), PN-05, PN-14 (an unsupported `Accept` answers JSON), PN-16 (lenient path
  ids). No case asserts against them.
- **Plain-text refusals.** Some `400` answers are plain text outside the envelope catalogue (PN-08,
  open question A8 of the contract). Cases expecting them assert the status and the state, not an
  envelope, until the catalogue answers A8.
- **Performance.** No latency budget is declared by the contract or the owner (M-21), so no case
  asserts one.

## Integrity questions

Asked for every write in this file (L-20, L-25, L-35, L-37, L-59):

- **Who else writes these fields?** `name` and `status` are also written by `PUT /pet` and
  `POST /pet/{petId}`; `photoUrls` by `PUT /pet` and `uploadImage`; `tags` and `category` by
  `PUT /pet`. Their siblings are in `registry/pet-update.md` (TC-PET-30 to TC-PET-35, TC-PET-41 to
  TC-PET-44, TC-PET-47). The form and XML media types of `PUT /pet` share the create's parser and
  are not designed separately; PN-18 is reproduced on the create only.
- **Preserve-on-omit.** Not asserted by a create. The update cases set a non-default value first.
- **Own records.** Every write case creates its pets with the builder, in its own id range, and
  asserts on those pets only. Seed pets are only read (TC-PET-18, TC-PET-27).
- **State after an error.** Every refused write reads its pet back and expects `404`, or, when the
  body carries no usable id, searches the case's unique `<TAG>` and expects no pet.
- **Cleanup.** Every case deletes the pets it created, or might have created through a departure,
  and confirms each delete with a read that answers `404`; the delete's `200` proves nothing
  (PN-22).
- **Records that break reads for others.** Only PN-18 is known to: TC-PET-16 is `@destructive`.
  The intake recorded no other stored departure (missing `name`, out-of-set `status`, empty
  `photoUrls`) that breaks a read. If automation sees one, that case becomes `@destructive` too.

## Case details

### TC-PET-01

- **Preconditions**: `default`; a pet `<PET_ID>` built with every field (category, tags with
  `<TAG>`, photo URLs, `<STATUS>` other than the builder default), not yet created.
- **Request**: `POST /pet` with the JSON body, then `GET /pet/<PET_ID>`.
- **Expected**: `200` and a body matching `Pet` on both; the response and the read-back equal the
  sent body field by field (every optional field honored).
- **Verification**: follow-up read compared with `expectSameState` and the pet field buckets.
- **Cleanup**: `DELETE /pet/<PET_ID>`, then a read answering `404`.
- **Tags**: `@smoke @data-integrity`
