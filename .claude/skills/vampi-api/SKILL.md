# VAmPI (vampi v0)

Generated by `npm run scaffold:service` on 2026-10-12. Facts marked _pending_ are filled in at the
first intake (`qa-intake`) and kept current by every later phase. Facts the pack already owns are
linked, not copied (`.claude/rules/documentation.md`).

## Contract

- Tracked copy: `services/vampi/openapi.yaml` (openapi-3.0, 14 operations). Its digest is
  `docs/discovery/vampi-digest.json`; `npm run contract:digest:live -- --service vampi` compares
  it with the deployed contract.
- Declared servers: `http://localhost:5000`.
- Departures from the contract: `services/vampi/docs/contract-notes.md`.

## Environments and writes

The environments where this pack runs, its base URL in each and whether writes are allowed there
are set in qa-config (`api.environments.<env>.packs.vampi`).

- **Two modes, two containers** of one image, both local only (`docker-compose.yml`, `npm run
  vampi:up` / `vampi:down`): `vampi-secure` (`vulnerable=0`, host port 5001) and
  `vampi-vulnerable` (`vulnerable=1`, host port 5002). `GET /` reports the mode in its
  `vulnerable` field. The vulnerable mode is deliberately insecure: never expose it beyond
  `127.0.0.1`.
- **No shared records.** Both containers are disposable; a restart (`vampi:down`, `vampi:up`)
  brings back an empty service. Cases create the users and books they use.
- **A fresh container has no tables**: every storage read answers `500` until `GET /createdb` runs
  (contract notes VN-01). `GET /createdb` is a write despite its method (VN-05): it creates the
  tables and seeds data. Never call it, or `GET /users/v1/_debug` (VN-06), from intake or a smoke
  check.

## Authentication and actors

Security schemes declared by the contract: `bearerAuth` (http, bearer, JWT).

- Tokens come from `POST /users/v1/login` (`{username, password}` → `auth_token`), so the pack
  uses the `login` strategy of `helpers/auth.ts`; the variable names are in the pack's qa-config
  entry. There is no static token to configure.
- A token lives `tokentimetolive` seconds (60, set in `docker-compose.yml`); the `login` strategy
  renews it after a `401`.
- No user exists on a fresh container: a run registers its own users before logging in. The
  implementation signs tokens with a constant key, so they can be forged in both modes
  ([books feature](../../../services/vampi/docs/features/books.md), G6).
- Actors for the books authorization cases: `anonymous`, `default` (the owner) and a second
  ordinary user; undecodable and expired tokens are sent explicitly by the case.

## Data

- Identity fields pseudonymized in evidence: `service.json` `identity_fields`.
- Evidence redaction masks body keys such as `password`, `secret` and `auth_token`
  (`helpers/redact.ts`), so a leaked book secret shows masked in evidence: a case proves a leak
  by comparing values in code, not by reading the evidence.
- Book titles are unique across all users (implementation): builders make them unique per run.
- Builders and shared-data guards: _pending_, written by `qa-automate` as cases need them.

## Errors

The error formats live in `services/vampi/error-envelopes.json` (measured 2026-10-12): `fail`
(`{status: "fail", message}`, the handlers' format), `problem` (`application/problem+json` from
the framework, for a missing token and an unknown path) and `server-error` (the Werkzeug debugger
HTML page). `401` comes in both `fail` and `problem` depending on what was wrong with the token
(contract notes VN-03).
